# Paper OS IDE 产品与架构规格

> 版本：0.1
> 状态：需求基线，供 Cursor 和后续维护者执行
> 产品：Paper OS

## 1. 产品定位

Paper OS 是一个 Windows 优先、local-first 的通用桌面 IDE，产品体验参考 VS Code 和 Cursor，但面向严肃文档、LaTeX、数学公式、代码和可验证交付进行增强。

LaTeX 不是唯一用途，也不是必须安装插件后才能使用的附加功能。它是内置 Pack 能力：用户可以直接编辑 `.tex`，调用本地编译器，生成 PDF，在 IDE 内预览，并在源码和 PDF 之间定位。与此同时，用户可以像使用普通 IDE 一样编写 Python、JavaScript、TypeScript、Markdown、数据文件和其他资源。

核心判断标准不是“界面像不像 VS Code”，而是以下工作闭环是否稳定：

`打开 Workspace -> 编辑 Resource -> AI 或手动修改 -> 运行/编译 -> 查看 Artifact -> 修复问题 -> 保存、回溯、交付`

## 2. 当前代码基线

当前仓库已经有一套可继续演进的基础，不应推倒重来：

- `apps/desktop/src/ide.jsx`：桌面 IDE 主界面、Workspace、文件树、Monaco、AI 面板、LaTeX 编译入口、PDF 预览、终端和状态栏。
- `apps/desktop/src/assets/ide.css`：桌面 IDE 的布局、主题、工作区面板和响应式样式。
- `apps/desktop/src/text-buffer.mjs`：文本缓冲区和脏状态管理。
- `app/server.mjs`：本地 Node 服务、Workspace API、编译、终端、AI 和 WebSocket 事件。
- `apps/desktop/build-ide.mjs`：把桌面 IDE 打包到 `app/ide/`。
- `web/`：网站、账号、公共页面和复用的前端依赖，不要把桌面 IDE 误改成营销站页面。
- `docs/ARCHITECTURE.md`、`docs/CAPABILITY_MAP.md`、`docs/HANDOFF.md`、`CONTEXT.md`：已有架构和术语来源，优先级高于临时实现想法。

已存在或部分存在的能力：Workspace Kernel、Pack、文件树、搜索、Monaco 编辑、文本缓冲、AI 流式对话、Apply Proposal、Tectonic/latex 编译探测、PDF 输出、SyncTeX、终端入口、Git 状态基础接口、测试和 Windows 启动壳。

不要把以下内容当作已经完成：完整 VS Code Extension API、全部调试器、远程开发、Webview 原生模块隔离、插件市场、云端同步、多人协作。

## 3. 目标工作模式

### 3.1 Agent 模式

Agent 模式是 Cursor 风格的协作工作台。用户可以描述目标，AI 负责理解 Workspace 上下文、制定计划、读取文件、提出修改、运行命令、编译和解释结果。用户也可以随时自己编辑，AI 不应锁住编辑器。

Agent 模式必须让用户看见：

- 当前任务和执行计划；
- 正在读取或修改的文件；
- 即将执行的命令及命令作用；
- Diff、Apply、Reject、Conflict、Rollback 状态；
- 编译日志、错误、警告和下一步建议；
- 当前使用的模型、运行时和是否为本地 Mock。

AI 不能把“生成了建议”伪装成“已经写入文件”。任何写入都要经过 Apply Proposal 或等价的可回溯 Edit Transaction。

### 3.2 Render 模式

Render 模式是文档和 Artifact 的可视化工作台，重点是：

- LaTeX 编译得到的 PDF；
- PDF 页码、缩放、基本导航和源码定位；
- Markdown、图片、数据和其他可预览资源；
- 公式实时草稿渲染；
- 编译状态、日志、错误和产物版本。

Render 模式不是只读模式，也不能阻止 AI 或用户编辑源码。模式只是界面重心：Agent 偏向任务和修改，Render 偏向结果和阅读。两者共享 Workspace、打开标签、AI、终端和状态。

### 3.3 模式切换原则

- 顶栏必须有清晰的 Agent/Render 分段切换。
- 切换不应丢失打开文件、编辑缓冲、AI 对话或编译结果。
- 选择应持久化到本机，下次启动恢复。
- 窄窗口下仍保留可识别的模式入口，可收缩为图标但不能消失。
- 当前模式应在 AI 面板和状态栏中再次显示，避免用户不知道当前工作重心。

## 4. LaTeX 与实时渲染规格

### 4.1 内置编译

- 用户不需要安装 LaTeX 插件才能编译。
- 编译器优先使用项目已经支持的 Tectonic，其次使用系统 Tectonic 或 latexmk。
- 编译路径必须限制在 Workspace 根目录内。
- 编译开始、标准输出、标准错误、完成、失败和超时都要有状态。
- 旧 PDF 只能在新编译成功后替换，失败时保留最近一次成功产物并明确标注过期。
- 缺少编译器或宏包时，要显示原因、检测结果和可执行的配置/安装入口。

### 4.2 PDF 预览

- 在 IDE 内预览，不要求用户切换到外部阅读器。
- 支持页码、缩放、关闭/恢复预览。
- 编译成功后自动刷新版本号或时间戳，避免浏览器缓存旧 PDF。
- PDF 无法加载时显示错误和产物路径，不显示空白区域。
- 如果有 SyncTeX，源码到 PDF 和 PDF 到源码都应可用；没有 SyncTeX 时要优雅降级。

### 4.3 实时公式预览

- 对 `$...$`、`$$...$$`、`\\(...\\)`、`\\[...\\]` 和常用 equation/align 环境提供草稿预览。
- 实时预览不是编译结果，必须标注 `Live` 或等价状态。
- KaTeX/MathJax 解析失败时显示原始公式和可读错误，不让整个面板崩溃。
- 复杂宏包、引用编号和版式最终以 PDF 编译结果为准。
- Render 模式没有 PDF 时，公式预览应成为有效的空状态替代，而不是空白页面。

## 5. 通用 IDE 能力

首期必须维护通用 IDE 身份：

- Workspace 创建、打开、切换、空状态、缺失目录状态；
- 文件树、创建、重命名、删除、打开、关闭标签、脏状态和保存；
- Monaco 语言编辑、语法高亮、查找替换、Quick Open、命令面板；
- 终端、运行命令、输出、错误和超时；
- Git 分支/状态/差异的基础可视化；
- 多种 Resource 类型：代码、Markdown、LaTeX、BibTeX、图片、PDF、CSV/TSV；
- 预览能力按 Resource/Pack 提供，不把 LaTeX UI 硬编码到所有 Workspace。

## 6. AI Harness 规格

Paper OS 需要一套可审计的 Harness，而不是只有一个聊天框。Harness 至少包含：

1. Context：Workspace、活动文件、选区、相关文件、Pack、当前错误和最近操作。
2. Plan：任务拆解、每一步状态、预计会访问/修改/执行的资源。
3. Tools：读取、搜索、编辑提案、终端、LaTeX 编译、PDF/日志查询。
4. Policy：Workspace 根目录限制、危险命令拦截、确认级别、超时和输出上限。
5. Transaction：多文件 Diff、Apply、Reject、冲突检测、失败回滚和历史记录。
6. Trace：会话 ID、模型、提示词版本、工具调用、结果、用户确认和错误。

默认交互应接近 Cursor：低风险读取可以自动执行；写文件、执行可能有副作用的命令、安装插件或改变环境时，必须以清晰的人类语言告知并提供确认/取消/回退入口。用户可在设置中调整自动化程度，但不应默认静默修改。

## 7. 插件兼容路线

### 7.1 首要目标

先兼容 VS Code 扩展包格式和常用 Extension API，支持本地 `.vsix` 安装、启用、禁用、卸载、版本信息和错误隔离。

### 7.2 兼容层边界

兼容层需要独立于 Workspace Kernel。扩展宿主不应直接获得任意文件系统或进程权限，所有能力走受控适配器：文件、配置、命令、语言服务、终端、调试、Webview、网络和原生模块。

### 7.3 兼容矩阵

按以下顺序验证，不以“宣称完整兼容”代替测试：

1. 主题、语言识别、语法高亮、格式化；
2. Git、LaTeX、Markdown、常用语言服务；
3. 命令、快捷键、状态栏、Tree View、Webview；
4. 调试器、任务、终端、远程能力；
5. 原生模块和平台相关扩展。

不支持的 API 必须有明确状态、原因和隔离机制；单个扩展失败不能拖垮主 IDE。

### 7.4 自研插件

自研插件使用同一个扩展包格式和发布流程：manifest、版本、权限、签名/校验、安装、更新、回滚。可以先使用本地目录或私有注册源，后续再接入公开市场。不要为自研插件另造一套无法迁移的 SDK。

## 8. UI 与交互规范

- 应用是安静、密集、可长时间使用的工具，不做营销页面。
- 延续 Horizon Atelier：深炭黑、暖琥珀、冷蓝信息色、玉绿色成功色、朱红错误色。
- 编辑器、日志和路径使用 JetBrains Mono；控制和正文使用 Inter/项目现有 UI 字体。
- 主编辑器、预览、Assistant、底部面板是稳定区域，使用边界线和分割器，不堆叠装饰卡片。
- 主按钮只用于明确动作；保存、关闭、搜索、切换、缩放优先使用图标按钮并提供 tooltip。
- 所有长路径、Workspace 名、文件名必须省略并提供 title，不得覆盖相邻内容。
- 任何加载、空、错误、成功和禁用状态都要有可读文本或图标语义。
- 尊重 `prefers-reduced-motion`，动画只表达状态变化，不在源码区域制造背景动效。

## 9. 响应式与设备适配

正式目标是 Windows 桌面窗口，但开发和验证必须覆盖：

- 1920x1080、1440x900、1280x800；
- 100% 和 125%/150% DPI；
- 窄窗口约 1024px 和约 800px 宽度；
- 编辑器、PDF、Assistant 三栏在空间不足时按优先级折叠，不能互相覆盖；
- 核心动作仍可通过键盘完成；
- 文字、按钮、标签和计数器不能溢出或挤压布局。

## 10. 错误、空状态和加载状态

所有主要区域都必须有明确状态：

- 未选择 Workspace：说明如何创建或打开；
- Workspace 没有文件：提供创建/导入入口；
- 没有活动文件：说明如何打开文件；
- 没有 PDF：显示编译入口和实时公式预览（若为 LaTeX）；
- 编译中：显示引擎、阶段、可取消/重试入口；
- 编译失败：显示错误、源码位置、日志和修复建议；
- AI 工作中：显示当前步骤，禁止重复提交但允许取消；
- AI 失败：保留上下文，允许重试或手动接管；
- 插件不兼容：显示扩展名、API、原因和隔离状态；
- 服务器/API 失败：显示可重试错误，不让整个界面白屏。

## 11. 验收标准

- [ ] 应用可启动，主窗口无白屏、卡死或关键区域缺失。
- [ ] 可创建、打开、切换 Workspace；缺失和空状态可理解。
- [ ] 可编辑并保存 LaTeX、代码、Markdown 等文件，脏状态正确。
- [ ] 无需 LaTeX 插件即可编译 `.tex`，显示日志、错误和警告。
- [ ] 成功编译后 PDF 在 IDE 内显示并刷新，失败不覆盖最近成功 PDF。
- [ ] 源码/PDF 定位可用；不可用时明确降级。
- [ ] Render 模式可实时显示公式草稿，失败显示公式级错误。
- [ ] Agent/Render 可切换、共享状态、可持久化，窄窗口可用。
- [ ] AI 显示上下文、计划、命令、Diff、Apply/Reject/Conflict/Rollback 和运行结果。
- [ ] AI 写入和高影响命令可确认、取消、重试、回退，不能静默伪成功。
- [ ] 终端、运行、Git 基础入口可用，错误可追踪。
- [ ] `.vsix` 安装生命周期和兼容矩阵有真实验证；不支持扩展不会拖垮主进程。
- [ ] 1920、1440、1280、1024 和窄窗口下无重叠、截断或不可达核心控件。
- [ ] 有对应单元/集成/UI smoke 测试和人工启动验证记录。

## 12. 当前范围与明确不做

本阶段做：通用 IDE 框架、双工作模式、内置 LaTeX/PDF/公式能力、可见 AI Harness、VS Code 兼容层基础、UI/响应式、测试和交接文档。

本阶段不承诺：一次性 100% 兼容所有 VS Code 扩展、完整远程开发、所有原生模块扩展无差异运行、云端编译、多人实时协作、移动端 IDE、逐像素复制 VS Code/Cursor。

任何未完成能力必须显示为 planned/partial，不得用静态按钮或假状态伪装成已交付。
